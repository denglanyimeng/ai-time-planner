### 技术栈结论

| 原文档要求 | 校准结论 |
|---|---|
| Go + Gin + GORM | ✅ 保留。已验证可编译、可拉依赖、可测试 |
| MySQL | ✅ 保留。已装且正在运行；已提供专用账号建库脚本 |
| Redis | ⚠️ **降级为可选**。见下方说明 |
| 前端「轻量化高性能」 | ✅ 保留，实现为零依赖原生单页应用（无构建、无 CDN、完全离线） |
| Docker | ❌ **不需要**。MySQL 与 Redis 均已有本机可用形态，装 Docker 纯属额外负担 |

**关于 Redis —— 我建议不把它当必需品，理由是实用而非偷懒：**

原文档把 Redis 定位为「计时状态、临时缓存、高频读取」。但经过计时方案的重新设计（见缺陷 #1），
**计时状态已经不再需要 Redis 承载**：真实耗时由「累计秒数 + 本轮开始时刻」两个数据库字段推导，
任意时刻都能精确还原。把权威状态放进 Redis 反而引入了一个风险 —— Redis 重启或 flush 会丢数据。

对单人本地工具而言，Redis 能带来的只有缓存加速，而本地 MySQL 查询本来就在毫秒级。
**因此实现上：Redis 配置项已预留（`REDIS_ENABLED`），但业务正确性完全不依赖它。**

## 二、原文档缺陷清单（核心结论）

### 🔴 硬性矛盾（1 处，必须改，否则需求无法同时满足）

| # | 文档原文 | 问题 | 处理方案 |
|---|---|---|---|
| 1 | 2.2.5「系统仅保留最近 21 天滚动数据，超 21 天自动清理」<br>同时 3.7 / 2.2.4「长期目标自动统计该标签**累计**学习时长」「进度对照参考」 | **这两条不可能同时成立。** 明细数据删掉之后，"累计学习时长"就永远算不出来了 —— 一个用了半年的目标，进度会永远停留在最近 21 天。 | 拆成两层：<br>• `tasks` 明细：21 天后清理<br>• `daily_tag_stats`（新增表）：按标签的每日汇总，**永久保留**<br>删除明细前先归集。长期进度因此可以无限期累计。 |

### 🔴 物理上无法实现（3 处，浏览器/单机环境下做不到）

| # | 文档原文 | 为什么做不到 | 处理方案 |
|---|---|---|---|
| 2 | 2.2.14「网页**彻底关闭** → 计时停止」 | `beforeunload` / `unload` **不保证触发**：页面崩溃、进程被强杀、移动端切后台、断电都不会触发。而且后台标签页会被浏览器节流，前端计时器本身就不可信。据此记录的时长必然失真。 | **服务端权威计时**：只存 `actual_seconds`（已累计）+ `run_started_at`（本轮开始）。前端每 30 秒心跳一次；超 90 秒无心跳，后台协程把计时**结算到最后一次心跳时刻**（不是当前时刻）并暂停。服务重启时同样按心跳回退结算，避免把停机时间算成学习时长。 |
| 3 | 2.2.9「超时未确认 → **AI 夜间**自动归为未完成事项」 | 需要一个**服务端定时任务**。原文档通篇没有提及任何调度机制。如果依赖前端，用户傍晚关掉网页后再没打开，这个归类永远不会发生。 | 新增后台维护协程 `RunJanitor`：每分钟检查一次，处理心跳结算、逾期归类、每日数据清理。<br>**并额外处理了「机器关机」场景**：启动时做一次追赶（`CatchUpMissedDays`），隔了三天才开机也能把漏掉的收尾补齐。 |
| 4 | 2.2.6「AI **动态监测**效率、主动优化提示」+「AI 一键对齐当前北京时间、**刷新全部时间戳**」 | 让大模型做时间算术。LLM 的算术能力不可靠，而且排程本身是**纯确定性计算**，交给模型只会引入错误、增加延迟与成本，没有任何收益。 | **职责拆分**：<br>• 第一段（不确定）：AI 只产出结构化草稿 —— 任务名、标签、预估时长、优先级。**prompt 中明确禁止输出任何时间点。**<br>• 第二段（确定）：`internal/planner` 纯函数引擎计算全部时间戳、判断溢出与超载。 |

### 🟡 缺失的落地定义（5 处，不补就会在开发中变成扯皮）

| # | 文档遗漏 | 处理方案 |
|---|---|---|
| 5 | **没有标签表**。3.9 要求「自定义标签名称 + 自定义标签颜色」，但第 5 章数据库设计里没有任何标签表，还把"标签颜色"冗余存在任务表里。 | 补齐 `tags` 表（`name` 唯一 + `color`），任务表通过 `tag_id` 关联。 |
| 6 | **没有存顺序的字段**。2.2.2 说「拖拽仅改顺序」，但 5.1 任务表里没有 order 字段 —— 顺序存在哪里？ | 补 `order_index`，并明确：**顺序是权威，时间戳是派生**。拖拽只改 `order_index` 不动时间戳；「一键对齐」按 `order_index` 重新派生时间戳。 |
| 7 | **周期任务没有幂等性**。3.5 说「每日打开网页自动加载当日周期任务」，但用户一天可能刷新十次页面 —— 会生成十份重复任务。 | 双保险：物化前先查当日是否已有该任务实例；数据库层用唯一索引 `(recurring_id, plan_date)` 兜底，并发请求也只成功一条。 |
| 8 | **「冲突」没有定义**。3.5 说「若与当日已有任务冲突 → 弹窗询问（覆盖/跳过）」，但没说怎样算冲突。 | 固定为**当日已存在同名任务**（忽略空白与大小写）。<br>不用"时间重叠"是因为：物化发生在排程之前，此刻新任务还没有时间戳，时间重叠根本无从判断。 |
| 9 | **「时间块」语义含糊**。2.1 说「自定义时间块」，2.2.16 又说「手动删减、调整时间块」—— 它到底是「可用时间段」还是「任务的固定占用」？ | 明确为**可用时间窗口**（例如 09:00–12:00、14:00–18:00），任务被排入其中。<br>并引出两条排程规则：**任务不拆分**（放不下就顺延到下一个窗口）；**休息间隔尽力满足**（若插入休息会导致任务放不下，就贴着上一个任务排，避免因休息制造无谓溢出）。 |

### 🟡 其他需要明确的细节

| # | 事项 | 处理方案 |
|---|---|---|
| 10 | **时区未定义**。通篇说"北京时间"，但没说数据怎么存。若机器时区设置错误或部署到 UTC 服务器，时间会整体偏移。 | 时间戳统一以 **UTC** 存储，展示层换算；「业务日期」用 `YYYY-MM-DD` 字符串；北京时区用**固定 +08:00**（中国无夏令时，可避免 Windows 上 `LoadLocation` 因缺 tzdata 而失败）。 |

| 12 | **双预估的偏差口径未定义**。用户没填自填预估时怎么算偏差？分母为 0 怎么办？ | 明确优先级：**用户自填 > AI 预估 > 兜底值**；任务时长收敛到 [1, 1440] 分钟；已超预估的任务在重排时保留 5 分钟最小占用，避免在时间轴上塌缩为零长度。 |
| 13 | **「未完成次日承接」自相矛盾**。2.1 说「自动归集、次日承接」，3.6 说「可一键加入今日计划」。 | 选择后者：**只入池，不自动插入次日计划**。<br>理由很实际：自动插入会在用户毫无察觉的情况下把第二天直接压到超载，与需求自己要求的「超载预警」正好相悖。另提供一键承接，采用**复制**而非移动，保留历史记录以便看出事情被推迟了几次。 |
| 14 | **「CSV 导入恢复」不可靠**。CSV 是无类型文本格式：分不清空串与 NULL、Excel 打开再保存会擅自改写日期格式与长数字、跨表关系无从表达。 | 备份包（ZIP）内同时放两种文件：<br>• `*.csv`：给人看、给 Excel 分析（带 UTF-8 BOM，中文 Windows 上不乱码）<br>• `backup.json`：给程序做**无损还原**<br>恢复只认 `backup.json`；若包里没有它会明确报错，而不是拿 CSV 凑合。 |
| 15 | **跨零点未定义**。时间块结束时间早于开始时间、任务跨过午夜，都没说怎么办。 | 时间块校验明确拒绝跨零点配置（返回清晰错误文案），而不是默默产生一个空窗口。 |
| 16 | **21 天清理会静默丢数据**。文档只说"支持手动导出备份"，没有提示机制。 | 清理前先归集汇总；同时在界面上把"导出备份"显式提供，并在 README 说明。 |

### 开发过程中被测试抓到的真实缺陷（举例）

写代码过程中，测试确实拦住了几个我自己写的 bug，它们都已修复：

1. **`NoRoute` 注册位置错误** —— 我原本把统一的 JSON 404 处理器写在"挂载前端目录"的分支里，导致未配置 `WEB_DIR` 时未知 API 路径会返回 `text/plain`，而前端统一按 JSON 解析错误响应，会解析失败。已改为**无条件注册**。
2. **超载判定边界** —— 我最初的测试断言"需求恰好等于可用时长算超载"是错的（此时计划刚好排满，完全可行）。已把语义固化为**严格大于**才预警，并补了边界测试。
3. **变量遮蔽** —— 在更新长期目标的处理器里我用了 `c` 作局部变量名，遮蔽了 Gin 的 `Context`，编译直接报错。

### 6.3 被测试抓出来的真实缺陷

这些不是假设，是我在开发过程中真实写错、又被验证拦下来的：

1. **GORM 列名映射错误（最隐蔽的一个）**
   我在模型里定义了 `AIPlanAdvice` 字段，并在更新语句里硬编码列名 `ai_plan_advice`。
   集成测试报 `no such column`。实测发现 GORM 实际生成的是 **`a_iplan_advice`** ——
   它对「连续大写字母后跟大写再跟小写」的断词规则与直觉不符，而同样格式的 `AISummary`
   却正确映射为 `ai_summary`。
   **修复方式不是改那一处字符串，而是给模型所有字段显式加 `column:` 标签**，
   让「Go 字段名 → 数据库列名」的映射完全确定、可审查，彻底消除这类对命名策略的依赖。

2. **`NoRoute` 注册位置错误**
   我把统一的 JSON 404 处理器写在了「挂载前端目录」的分支里，导致未配置 `WEB_DIR` 时，
   未知 API 路径会退化成 `text/plain` 404 —— 而前端统一按 JSON 解析错误响应，会解析失败。
   已改为无条件注册。

3. **超载判定边界**
   我最初的测试断言「需求恰好等于可用时长算超载」是错的：此时计划刚好排满，完全可行。
   语义已固化为一律**严格大于**才预警，并补了边界测试。

4. **变量遮蔽**
   在更新长期目标的处理器里，我用 `c` 命名了局部变量，遮蔽了 Gin 的 `Context`，编译直接报错。

### 6.4 一个值得记下的教训

端到端脚本第一次跑出 12 个失败。逐个查证后发现，**其中 10 个是测试脚本自身的问题**，
只有 2 个需要进一步定位：

- Windows PowerShell 5.1 的 `Invoke-WebRequest` 会**忽略 `Content-Type` 里的 charset**，
  按系统 ANSI 代码页（中文系统即 GBK）解码文本响应，导致 UTF-8 中文全部乱码、
  JSON 解析失败；请求体里的中文还会被替换成 `?`。
- 我设的测试时间块是 09:00–12:00，而脚本运行时刻是下午 16:31 —— 该时段已经过去，
  可用时间为 0，排程自然把所有任务归入未完成。**这是测试设置错误，服务端行为是对的。**
- 剩下 2 个源于 PowerShell 表达式输出会把**单元素数组解包成标量**，
  于是 `$x.Data.Count` 取不到值。已统一改为 `@($x.Data).Count` 强制成数组。

这件事本身印证了报告开头的那句话：失败先别急着改代码，先分清**哪些是产品缺陷、
哪些是验证手段自身的缺陷**。把工具的问题当成产品的问题去改，会把正确的逻辑改坏。
